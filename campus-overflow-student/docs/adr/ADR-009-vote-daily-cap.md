# ADR-009：投票声誉每日上限与悬赏冻结积分模型

**状态**：已接受 ｜ **驱动特征**：安全性、可测试性 ｜ **相关场景**：QS-05（反作弊）、QS-06（悬赏结算）、FF-8（对账）

## 背景

声誉直接激励社区行为，恶意用户可通过互刷投票快速抬高声誉（Sprint 3 实现 VoteCastEvent 消费时暴露该风险）；同时悬赏机制需要在"发起"与"结算/到期"之间保证积分不会透支或被重复使用——若在发起时直接扣减声誉，则声誉与账本的对账不变量（余额 = 流水之和）会被破坏。

## 决策

1. **投票声誉每日上限（反作弊）**：每人每个 UTC 自然日因"被投票"获得的正向声誉增量最多 200（`ReputationRulebook.DAILY_VOTE_CAP`）。消费 VoteCastEvent 时：先按 `voteEffect(新值) − voteEffect(旧值)` 计算增量，再以 `sumPositiveVoteDeltaSince(userId, 当日 UTC 零点)` 为已用额度，用 `applyDailyCap` 截断正向增量；负向增量（被踩）不受限。
2. **悬赏冻结积分模型**：教师开户发放悬赏积分（可用 + 冻结 = 总量，与声誉是两种货币）。发起悬赏时把积分从"可用"转入"冻结"；结算时发起人的冻结积分转出，获奖者以 `BOUNTY_AWARDED` 流水获得等额**声誉**；到期未采纳（或发起人自己的回答被采纳）则冻结积分退回可用。所有状态变更与积分变动在同一事务。

## 后果

- 正面：互刷投票的收益被严格封顶且可配置；悬赏全程不触碰声誉账本，`余额 = 流水之和` 的对账不变量保持简单；冻结/退款逻辑可单元测试（纯内存对象即可覆盖）。
- 负面：每日上限的判定依赖账本聚合查询 `sumPositiveVoteDeltaSince`（一次 SQL 聚合，开销可控）；积分与声誉双轨制需要向用户解释清楚（在声誉档案中分别展示 available/frozen 与 reputation）。

## 被否决的替代方案

- **不做上限，靠人工巡查**：无法规模化，且作弊收益实时到账、事后追回困难。
- **悬赏直接扣声誉**：破坏账本对账不变量；声誉是终身成就，不应因悬赏消耗而下降，语义混乱。
- **上限按自然日（Asia/Shanghai）而非 UTC**：全库时间统一 UTC（部署与迁移约定），按本地日会让边界随部署时区漂移，测试不可复现。
