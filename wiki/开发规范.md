# 开发规范

> 目标：让代码在**半年后**还能被自己和队友改动。规范不是审美，是用来降低评审成本的约定。

## 1. 代码放哪：先按层，再按聚合

```
co-qa/
├── co-qa-api/            QuestionSummary、AskQuestionCommand、评价事件契约
├── co-qa-domain/         Question、Answer、Vote、Tag；仓储接口 QuestionRepository
├── co-qa-application/    QuestionApplicationService（@Transactional 在这一层）
├── co-qa-infrastructure/ QuestionJpaEntity、JpaQuestionRepository、SearchProjectionJdbc
└── co-qa-interfaces/     QuestionController、请求/响应映射
```

判断标准：

| 你想写的东西 | 放这里 |
| --- | --- |
| “这条规则永远成立”（不能自投、只能采纳一次） | `domain` 的聚合方法 |
| “做这件事要先查 A 再改 B”（跨聚合编排） | `application` 的服务 |
| SQL / Redis / 外部 API | `infrastructure` |
| 参数校验、HTTP 状态、DTO 转换 | `interfaces` |
| 另一个上下文要用的数据结构 | 那个上下文的 `-api` |

## 2. 领域层三条铁律

1. **零框架**：不出现 `@Entity`、`@Service`、`@Valid`、`ObjectMapper`。ArchUnit 会拦住你（FF-1）。
2. **不返回 null**：用 `Optional` 或抛 `DomainException`；集合返回空集合。
3. **不变式写在构造/工厂与行为方法里**，不要指望调用方“记得检查”。

```java
// 好：规则在聚合内，无法绕过
public void accept(AnswerId answerId, Actor actor) {
    if (!canManage(actor) && !isAsker(actor)) throw new DomainException("QA-3002", "只有提问者或课程管理者可以采纳最佳答案");
    if (this.acceptedAnswerId != null)  throw new DomainException("QA-2001", "该问题已采纳过最佳答案，不能更改");
    ...
}
```

## 3. 命名

| 元素 | 约定 | 例 |
| --- | --- | --- |
| 聚合根 | 单数名词 | `Question`、`Bounty` |
| 值对象 | 业务含义明确的单数 | `ReputationDelta`、`SearchQuery` |
| 用例服务 | `<名词>ApplicationService` | `QuestionApplicationService` |
| 领域服务/策略 | `<职责>Policy` / `<职责>Rulebook` | `BadgePolicy`、`ReputationRulebook` |
| 事件 | 过去式 + `Event` | `AnswerAcceptedEvent` |
| 仓储接口 | `<聚合>Repository`（domain 层） | `QuestionRepository` |
| 集成事件处理器 | `<上下文>EventHandlers` / `<职责>Projector` | `ReputationEventHandlers`、`SearchIndexProjector` |
| 错误码常量 | 与业务码同名场景 | `QA-1015` |

避免：`Manager`、`Helper`、`Util`、`Data`、`Info` 这类无信息量的后缀。

## 4. 提交与分支

| 项 | 约定 |
| --- | --- |
| 分支 | `feature1` / `feature2` 各自主线开发；临时分支 `feat/<主题>` |
| 合并 | PR → 至少 1 人 review LGTM → 合并 `main`；不直接 push `main` |
| 提交信息 | `feat:` / `fix:` / `docs:` / `ci:` / `build:` / `refactor:` / `test:` + 一句话 |
| 粒度 | 一个提交只做一件事；重构与功能分开提交 |
| 提交前 | Husky `pre-commit` 自动跑 `lint-staged`（ESLint --fix + Prettier），失败即拦 |

示例：

```
feat(s3): 悬赏结算改为事件驱动，支持自答退款
fix(qa): 修正采纳后重复加分（差量结算）
docs(wiki): 补充错误码分段说明
```

## 5. 测试怎么写

- **领域测试**是规格说明：一个测试只断言一条规则，命名写成“条件 + 期望”；
- **应用层测试**用手写 Test Double（`InMemoryQuestionRepository`），**不启 Spring 容器**，保持毫秒级；
- **不要修改已有断言的期望值**来让测试变绿——那等于改需求；确实认为断言错了，在 PR 里说明并找老师确认；
- 新增分支/边界就补测试，覆盖率门禁是 0.70 的下限而不是目标。

```java
@Test
void accept_byNonAskerWithoutManageRight_isRejected() {
    DomainException ex = assertThrows(DomainException.class, () -> question.accept(answerId, studentActor));
    assertEquals("QA-3002", ex.code());
}
```

## 6. 前端约定

- 严格类型：`tsconfig` 开了 `noUncheckedIndexedAccess`，数组下标要先判空；
- 组件只做展示与交互，**业务判断留给后端**；错误统一从 `ProblemDetail.code` 分支；
- 所有请求走 `api.ts`，不在组件里裸写 `fetch`；
- 提交前跑 `npm run lint && npm run typecheck && npm run build`。

## 7. 完成定义（DoD）

一个任务算“完成”，需要全部满足：

- [ ] 领域规则有测试，且测试名能读出业务含义
- [ ] `mvn test` 全绿；`ArchitectureTest` 通过
- [ ] `mvn verify -DskipITs -Djacoco.skip=false` 覆盖率仍过 0.70
- [ ] 新增业务错误码已登记（前缀/段/文案）
- [ ] 接口变更同步 Swagger 注解与前端类型
- [ ] 文档：影响架构的写 ADR；影响用法的改 Wiki
- [ ] PR 描述写清“改了什么、为什么、怎么验证”

## 8. 评审看什么

`docs/team/review-checklist.md` 有 6 个维度 30+ 条目，核心是四条：

1. **边界**：有没有跨层/跨上下文的偷偷依赖？
2. **规则**：业务判断是否都在领域层，能否被绕过（比如直接改 setter）？
3. **失败路径**：异常码对不对、事务边界是否覆盖事件写入？
4. **可测性**：这段逻辑能不能不启容器就测？

反模式（评审直接打回）：Controller 里写业务判断、domain 引 Spring 注解、跨上下文直接 new 对方 Service、为了过测试改断言、`catch (Exception e) {}`。
