# 测试与质量门禁

## 1. 三层测试，各管一段

| 层 | 测什么 | 怎么测 | 速度 |
| --- | --- | --- | --- |
| **领域测试** | 聚合的不变式、状态机、规则边界 | 纯 JVM，`assertThrows` + 断言错误码 | 毫秒 |
| **应用层测试** | 用例编排、事件发布、跨上下文调用 | 手写 Test Double（内存仓储、假发布器），**不启 Spring** | 毫秒 |
| **集成测试（IT）** | 真实 MySQL/Redis 上的端到端链路 | Testcontainers 拉起真实中间件 | 分钟级 |

为什么强调“应用层测试不启容器”：一旦 `@SpringBootTest` 满天飞，测试会从毫秒变秒级，人就懒得跑，反馈环就断了。

## 2. 命令速查

```bash
cd backend

# 全部单元测试（不需要 Docker）
mvn test

# 单个上下文 / 单个测试类
mvn test -pl co-qa/co-qa-domain -Dtest=QuestionTest

# 架构约束
mvn test -pl co-bootstrap -Dtest=ArchitectureTest

# 覆盖率门禁（跳过 IT，跑 JaCoCo 校验）
mvn verify -DskipITs -Djacoco.skip=false

# 端到端集成测试（需要 Docker）
mvn verify

# 只跑 IT（CI 里的用法）
mvn verify -Dsurefire.skip=true
```

```bash
cd frontend
npm run lint        # ESLint
npm run typecheck   # tsc --noEmit
npm run build       # tsc -b && vite build
```

## 3. 覆盖率门禁怎么算

父 POM `backend/pom.xml` 里有属性 `domain.coverage.minimum`，JaCoCo 只对 **`-domain` 模块**做主源集的行覆盖率校验：

| 上下文 | 领域层行覆盖率（当前） |
| --- | --- |
| Identity | 75.7% |
| Q&A | 80.6% |
| Reputation | 71.6% |
| Discovery | 81.4% |

- 门禁值已从骨架的 `0` 提升到 **`0.70`**；
- 只卡领域层是刻意的：控制器和 JPA 适配器写起来机械、测起来昂贵，**业务规则才是要守的地方**；
- 覆盖率掉了不会自动变绿——`mvn verify` 直接失败，CI 红。

### 提高覆盖率的正经做法

1. 先看 JaCoCo 报告 `target/site/jacoco/index.html` 里**标红的行**；
2. 那些行通常是“没测的边界”：空集合、上限值、重复操作、权限不足；
3. 为每个边界写一条**断言具体错误码**的测试，而不是补一个“跑一遍不出异常”的空测试。

### 不要这样做（会被评审打回）

- 把门禁值调回 0；
- 写没有断言的测试去“刷行数”；
- 用 `@Disabled` 屏蔽失败测试；
- 修改已有断言的期望值让它变绿。

## 4. 架构测试

`ArchitectureTest` 是**可执行的架构文档**：它把“领域层不能依赖 Spring”“跨上下文只能经 api”“表名要带前缀”写成了断言。违反时失败信息会直接告诉你哪条规则（FF-1/FF-4/FF-5/…）被破坏。

它和普通测试一样跑在 `mvn test` 里，所以**架构腐化会在提交前就暴露**。

## 5. 集成测试与 CI 的关系

| 阶段 | 命令 | 依赖 Docker | 目的 |
| --- | --- | --- | --- |
| 单元测试 | `mvn test` | 否 | 逻辑正确性 |
| 覆盖率门禁 | `mvn verify -DskipITs -Djacoco.skip=false` | 否 | 质量下限 |
| 集成测试 | `mvn verify`（CI 中 `-Dsurefire.skip=true`） | **是** | Flyway 迁移、发件箱投递、投影、事务边界的真实验证 |

本地没有 Docker 时，只有最后一步跑不了，前两步随时可跑——这也是把 IT 和单测分开的原因。

当前状态：端到端链路（注册 → 提问 → 回答 → 采纳 → 声誉 +15 → 徽章 → 搜索命中 → 通知）按 IT 断言逐项对齐，但**本机未装 Docker，本地未跑通**，以 CI 为准。

## 6. 静态检查

| 工具 | 位置 | 检查什么 |
| --- | --- | --- |
| ArchUnit | `co-bootstrap/src/test` | 分层、跨上下文、表名前缀、无环 |
| JaCoCo | 父 POM | 领域层行覆盖率 |
| ESLint（typescript-eslint + react-hooks） | `frontend` | 未使用变量、hook 依赖、渲染纯度 |
| Prettier | `frontend` + Husky | 格式统一 |
| TypeScript strict + `noUncheckedIndexedAccess` | `frontend` | 空值安全 |
| SonarQube 配置 | `backend/sonar-project.properties` | 供团队实例扫描（未上传结果） |

## 7. 测试写得好的标志

- 看测试名就知道业务规则：`accept_byNonAskerWithoutManageRight_isRejected`；
- 一个测试只断言一件事，失败时能直接定位；
- 断言具体的 `code()`（`QA-3002`），不是“抛了异常就行”；
- 测试之间无顺序依赖，可单独运行、可并行。
