# 项目概览

## 1. 要解决什么问题

高校课程里的问答几乎都在微信群/QQ 群里发生：同一个问题被问十遍、答案沉底、老师没法沉淀知识、好回答没有回报。CampusOverflow 把这些搬到一个**按课程组织**的问答社区里：

- 学生绑定学号/工号注册，按课程加入，在课程范围内提问、回答、投票、采纳；
- 教师是课程管理者，可以认证答案、发起悬赏、管理成员；
- 系统按**信誉账本**结算声誉、发放徽章、维护排行榜；
- 中文全文检索、相关问题、@提及与通知把内容真正“用起来”。

## 2. 四个限界上下文

| 上下文 | 职责 | 主要聚合 | 对外提供 |
| --- | --- | --- | --- |
| **Identity** | 账号、认证、课程、角色与认证状态 | `User`、`Course`、`CourseMember` | 登录态、`Actor`（当前用户+角色）、课程成员校验 |
| **Q&A** | 提问、回答、评论、标签、投票、采纳 | `Question`、`Answer`、`Comment`、`Vote`、`Tag` | 问题/回答的读写与状态机 |
| **Reputation** | 积分账本、规则引擎、徽章、悬赏、排行榜、对账 | `ReputationAccount`、`Bounty`、`ReputationRulebook`、`BadgePolicy`、`AcademicTerm` | 声誉查询与流水、榜单、悬赏 |
| **Discovery** | 中文检索、相关问题、@提及、通知 | `SearchQuery`、`Notification`、`RelatedQuestionPolicy`、`MentionParser` | 搜索结果、通知中心 |

依赖方向：**只允许通过对方的 `-api` 模块（发布语言）调用**，跨上下文不共享领域对象。Q&A / Reputation / Discovery 之间的协作靠**领域事件**，不靠直接调用。

## 3. 一次完整链路

```
1. 学生注册            Identity 发布 IdentityRegistered
2. 开户                Reputation 监听 → 建账户，初始 1000 分（教师）
3. 提问                Q&A 校验课程成员身份（经 Identity api）
4. 回答 / 投票         一人一票，可改投/撤销；不能给自己投票
5. 采纳                Q&A 发布 AnswerAccepted
6. 结算                Reputation：采纳 +15（自问自答 0）→ 徽章 FIRST_ACCEPTED
                       → 若有悬赏则结算给回答者
7. 投影                Discovery：更新搜索索引、生成通知
8. 查询                排名、检索、通知中心、相关推荐
```

> 所有跨上下文事件都走**事务性发件箱**（ADR-002）：业务写入与事件写入同一个事务，中继异步投递，消费端必须幂等。

## 4. 技术栈

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 语言/运行时 | Java 21 | `java.version=21`，用 record、sealed、模式匹配 |
| 后端框架 | Spring Boot 3 | Web、Security、Data JPA、Actuator |
| 构建 | Maven 多模块 | **27 个 `pom.xml`**：6 个聚合模块 + 4 上下文 × 5 层 + shared-kernel + bootstrap |
| 数据库 | MySQL 8.0.39 | `utf8mb4`，`ngram_token_size=2` 支持中文全文检索（ADR-005） |
| 缓存/会话 | Redis 7 | 服务端会话（ADR-003） |
| 迁移 | Flyway | `ddl-auto: none`，表结构只由迁移脚本管理 |
| 文档 | springdoc-openapi | `/swagger-ui.html` |
| 架构守卫 | ArchUnit | 领域层零框架依赖、依赖由外向内、发布语言轻量 |
| 覆盖率 | JaCoCo | 领域层门禁 `domain.coverage.minimum` |
| 集成测试 | Testcontainers | 真实 MySQL + Redis |
| 前端 | React 18 + TypeScript + Vite | 7 个页面 + 认证上下文 + 单文件 API 客户端 |
| 部署 | Docker / Compose / Nginx | 多阶段镜像，SPA fallback |
| 可观测 | Prometheus + Grafana | `observability` profile 按需启动 |
| 流水线 | GitHub Actions | 后端、前端、镜像、部署四段 |

## 5. 架构决策一览（`docs/adr/`）

| 决策 | 一句话 | 影响 |
| --- | --- | --- |
| 包结构按上下文×层切分 | `com.campusoverflow.<context>.<layer>` | 模块边界即编译边界 |
| 事务性发件箱 | 业务数据与事件同事务落库，中继投递 | 不丢事件，但要求消费端幂等 |
| 声誉账本 | 只追加的流水 + 账户余额，两者同事务 | 可对账、可追溯，不允许直接改余额 |
| 契约优先 | 先定 `-api` 发布语言，再实现 | 跨上下文解耦，前端契约稳定 |
| 领域与持久化分离 | 领域模型不出现 JPA 注解 | 领域可脱离框架单测（ArchUnit FF-1） |
| 投票每日上限 | 每日正向得分封顶 200，冻结积分模型 | 防刷分，见 ADR-009 |
| 软删除 | 内容删除保留行，用标记位过滤 | 审计可查，查询需带条件 |
| 中文全文检索 | MySQL ngram + 停用词关闭 | 必须用 compose 的 MySQL，自建库要同步参数 |

> 当前 `docs/adr/` 收录了其中 6 份文件（含 `ADR-002-package-structure.md`、`ADR-009-vote-daily-cap.md`）；其余决策在 `docs/adr/README.md` 索引与代码注释中可追溯。
